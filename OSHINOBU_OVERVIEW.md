# Oshinobu — обзор проекта

Живой документ. Раньше на него ссылался комментарий в `client/lib/services/message_router.dart`,
но сам файл был утерян — этот файл его восстанавливает и должен пополняться по ходу работы
над проектом (а не только читаться).

## Что это

Приватный E2EE-мессенджер: 1:1-переписка, шифрование Double Ratchet + X3DH (протокол в духе Signal,
реализован с нуля в `client/lib/crypto/`, без сторонней crypto-библиотеки для самого протокола).
Регистрация только по инвайт-коду — открытой публичной регистрации нет.

- **Клиент** — Flutter/Dart, `client/`. Сейчас в закрытом тестировании (closed testing) в Google Play.
- **Сервер** — Go, `server/` (основной код — `server/internal/`). Работает на VPS в Москве,
  владелец подключается и деплоит вручную по SSH.
- Сервер — только маршрутизатор/хранилище опaque-конвертов: ключи, plaintext сообщений и
  медиа-контент серверу в норме недоступны (см. раздел "Границы доверия" ниже — где это
  нарушается и почему).

## Архитектура клиент/сервер

```
Клиент A                         Сервер (Go)                      Клиент B
--------                         -----------                      --------
X3DH/Double Ratchet   --WS-->    маршрутизация по device_id --WS--> расшифровка,
(crypto/*.dart)                  + очередь на диске, если          message_router.dart
                                  получатель офлайн
                                  (pending_messages, ack за 5с)
```

Ключевое: сервер не знает, доставлено ли сообщение НА САМОМ ДЕЛЕ (расшифровано клиентом) —
только "ack пришёл за 5 секунд или нет" (`server/internal/api/websocket.go`). Если ack
потерялся (не сама доставка, а именно ack), сервер честно не может отличить это от "клиент не
получил" и передоставит то же сообщение с новым `DeliveryId` при следующем реконнекте.
**Дедупликация — полностью на клиенте**, по `message_id` внутри уже расшифрованного конверта
(`ChatStore.addMessage`/`addMessages`), не по транспортному `DeliveryId`.

## Крипто-слой (клиент)

- `crypto/x3dh.dart` — согласование корневого ключа (X3DH: identity + signed-prekey +
  опциональный one-time-prekey).
- `crypto/double_ratchet.dart` — `RatchetState`, шаг рэтчета на приём/отправку, защита от
  replay (`messageNumber < receiveMessageNumber` → `AlreadyProcessedException`).
- `crypto/key_store.dart` — identity-ключ (Ed25519) + отдельный подписанный X25519-ключ
  ("identity_dh") для самого DH (Ed25519 сам по себе для DH не годится — сознательное решение,
  не недоделка).
- `crypto/session_store.dart` — персистентное состояние ратчета per-remote-device.
- `services/message_router.dart` — единая точка входа для всех входящих WS-конвертов:
  расшифровка, dispatch по `InnerMessage.type` (text/media/reaction/pin/edit/delete/delete_chat/
  clear_chat/read_receipt), auto-recovery сессии после 3 подряд decrypt-failure
  (`_onDecryptFailure` → `session_reset`).
- `services/send_queue_processor.dart` — надёжная исходящая очередь на диске, элемент
  уходит только по реальному ack от сервера.

## Известные особенности / принятые решения (не баги)

- Домен сервера в `client/lib/config.dart` — `ee2e.oshino.space` (буквы переставлены
  относительно "e2ee"). Не опечатка, менять не нужно.
- Звонки: сигналинг (`call_offer`/`answer`/`ice`) теперь ТОЖЕ шифруется той же Double Ratchet
  сессией, что и обычные сообщения (см. `call_service.dart` `_encryptCallSignal`/
  `_decryptCallSignal`) — `call_id`/`sender_device_id`/`type` остаются снаружи в открытом виде
  (нужны серверу для `PendingCallRegistry`), сервер при этом не менялся вообще.

## Границы доверия

Сервер не должен видеть: текст сообщений, медиа-контент, ключи сессий, содержимое звонков
(SDP/ICE). Сервер осознанно видит: логины, device_id, кто с кем переписывается/созванивается
(метаданные), call_id (нужен для офлайн-очереди звонков).

## Хранилище медиа и передача файлов (инфраструктура)

Все медиа/файлы шифруются на клиенте (AES-GCM, `crypto/streaming_file_cipher.dart` для
чанковых, `crypto/media_cipher.dart` для мелких) ещё ДО загрузки. Сервер и хранилище видят
только шифротекст; ключ расшифровки едет внутри Double-Ratchet-конверта.

**Физическая топология (обновлено 2026-09-05, миграция Токио→Осака — см. отдельный раздел
ниже «Миграция relay-VPS с Vultr/Tokyo на Sakura/Osaka»).** Схема — «звезда» с NAS в центре;
московский и осакский серверы между собой НЕ связаны, оба независимо ходят в MinIO по своим
FRP-туннелям (NAS сам звонит наружу к обоим `frps`).

- **MinIO** — контейнер `minio-e2ee` на NAS (TrueNAS SCALE на Terramaster F4-423, 32 ГБ RAM)
  в **Японии**, за домашним роутером без белого IP. Данные `/mnt/tank/e2ee/minio`, бакет
  **`e2ee-media`** (ключ объекта = случайный UUID `media_id`; человекочитаемое имя файла
  хранится отдельно в колонке `object_key` таблицы `media_files`). Порты 9000/9001 доступны
  только в LAN + по FRP; в интернет не выставлены. Рут-креды MinIO — на NAS в
  `/mnt/tank/e2ee/scripts/MinIO/.env`.
- **Московский VPS** (`ee2e.oshino.space`, 195.19.66.107, Free Tier: 1 vCPU / 1 ГБ / 10 ГБ —
  очень слабый) — Go-сервер, Postgres, nginx, `frps` (бинарь, `/e2ee/frps/frps.toml`,
  `e2ee-frps.service`, `bindPort=7000`). Достаёт MinIO по FRP на `127.0.0.1:9000`
  (NAS-контейнер **`frpc-e2ee-msk`**, скрипт `/mnt/tank/e2ee/scripts/frpc/frpc_e2ee.sh`,
  проксирует `minio-api` 9000 и `minio-console` 9001). `proxyBindAddr = "127.0.0.1"` в
  `frps.toml` — проброшенные порты слушают только localhost, в интернет не торчат
  (раньше 9000/9001 висели на публичном IP — закрыто 2026-09-03).
- **Osaka VPS** (`files.oshino.space`, `49.212.216.161`, さくらのVPS/Sakura Internet, Осака
  зона 3, 1G-план ~935¥/мес, 2 vCPU / 1 ГБ / 50 ГБ SSD, Ubuntu 24.04) — до 2026-09-05 эту роль
  играл Vultr Tokyo (`202.182.112.9`), см. раздел миграции ниже. nginx (TLS Let's Encrypt через
  `--nginx`, авто-renew; `proxy_request_buffering off`, `proxy_buffering off`,
  `client_max_body_size 0`, `proxy_set_header Host $host` — критично для SigV4) +
  `frps` (`e2ee-frps.service`, `bindPort=7000`, `proxyBindAddr = "127.0.0.1"`). NAS-контейнер
  **`frpc-e2ee-osaka`** (переименован из `frpc-e2ee-tokyo`, скрипт+конфиг
  `/mnt/tank/e2ee/scripts/frpc-osaka/`, только `minio-api` 9000 — консоль не пробрасываем)
  держит туннель MinIO → Osaka на `127.0.0.1:9000`, nginx его проксирует. FRP-токен свежий,
  сгенерирован заново при миграции (не унаследован от Vultr). У Sakura ЕСТЬ СВОЙ ОБЛАЧНЫЙ
  firewall ("パケットフィルター" в панели) ОТДЕЛЬНО от `ufw` внутри сервера — порт нужно
  открывать в ОБОИХ местах, иначе тихо режется на уровне облака ещё до `ufw` (реальный кейс
  при миграции — забыли 443/tcp именно в `ufw`, при том что в панели он уже был открыт).
  **Харднинг Osaka:** ufw (22/80/443/7000/tcp + 443/udp) + панель Sakura (те же порты),
  fail2ban (поставлен установщиком AmneziaWG, см. ниже), SSH — по ключу (тот же
  `e2ee_vps.pub`, что и у остальных VPS проекта), пароль отключён ещё на этапе создания
  сервера в панели Sakura.
  **HTTP/3.** Штатный nginx 1.24.0 из репозитория Ubuntu 24.04 — БЕЗ `--with-http_v3_module`
  (в отличие от Vultr/Ubuntu 26.04, где штатный пакет уже был с QUIC) — пришлось ставить
  nginx из официального репозитория **nginx.org** (mainline, `deb ... nginx.org/packages/
  mainline/ubuntu noble nginx` + apt-pinning priority 900), версия 1.31.5, уже с
  `with-http_v3_module`. **Важный побочный эффект**: пакет nginx.org при установке
  ЗАМЕНЯЕТ `/etc/nginx/nginx.conf` на свой дефолтный, который инклюдит только
  `/etc/nginx/conf.d/*.conf`, БЕЗ Debian-style `sites-enabled` — конфиг сайта после апгрейда
  молча переставал загружаться, пока вручную не дописали `include /etc/nginx/sites-enabled/*;`
  обратно. В остальном те же строки, что и на Vultr: `listen 443 quic reuseport;`
  (+ `[::]:443`), `http3 on;`, `quic_retry on;`, `add_header Alt-Svc 'h3=":443"; ma=86400'
  always;`. Подтверждено: `curl -sI .../minio/health/live` отдаёт заголовок `Alt-Svc`.
- **DNS:** `files.oshino.space A → 49.212.216.161` в Route53 (обычная A-запись, зона
  `oshino.space` осталась на Route53 — не мигрировали из-за почты reg.ru + старого
  не-e2ee сайта `oshino.space` + авто-renew TLS).

**Поток данных — presigned URL (главное решение):** байты файлов идут **напрямую
клиент → `files.oshino.space` → Osaka → FRP → NAS**, минуя московский сервер — **когда клиент
вообще может достучаться до relay-VPS напрямую.** До 2026-09-05 роль relay играл Vultr Tokyo —
заменён на Sakura Osaka (см. отдельный раздел про миграцию ниже), сам механизм не изменился.
У пользователей РФ без VPN это не всегда так (см. раздел «Ускорение передачи файлов» ниже —
DPI резал TLS-рукопожатие конкретно к Vultr/Tokyo минимум у части провайдеров; для нового
relay на Sakura отдельно не проверялось, см. миграцию) — тогда клиент откатывается на relay
через Москву (тот самый слабый VPS, которого этой схемой пытались избежать). Москва в остальном:
- подписывает presigned-URL (`server/internal/api/media_presign.go`, второй minio-клиент с
  endpoint из `MINIO_PUBLIC_ENDPOINT` + `MINIO_PUBLIC_SECURE=true` — реально никуда не
  коннектится, подпись SigV4 это локальная HMAC-криптография; срок ссылки `presignExpiry =
  2h`). Работает потому, что и Москва, и MinIO знают один секрет `oshino-server` независимо —
  переговоров между ними при подписи/проверке нет;
- ведёт строку в `media_files` (кто загрузил / кому / object_key = имя файла / размер
  шифротекста);
- делает служебные multipart-вызовы к MinIO по FRP (init/complete/list/StatObject — крошечные).

Московский `.env` (кроме прежнего): `MINIO_ACCESS_KEY=oshino-server`, `MINIO_SECRET_KEY=…`
(scoped-юзер вместо рута), `MINIO_PUBLIC_ENDPOINT=files.oshino.space`, `MINIO_PUBLIC_SECURE=true`.
`MINIO_ENDPOINT=127.0.0.1:9000` (через FRP) и `MINIO_BUCKET=e2ee-media` — без изменений.

**Эндпоинты:**
- Нечанковый файл (≤ 20 МБ): `POST /upload-media/presign` → `{media_id, url}` (строку в БД
  ещё НЕ создаёт) → клиент PUT байт на `url` → `POST /upload-media/{id}/finalize`
  (`{recipient, size_bytes, file_name}`) — сервер `StatObject` проверяет, что объект
  нужного размера долетел, и только тогда пишет строку в БД (без finalize — висячих строк
  без объекта не остаётся).
- Чанковый файл (> 20 МБ): `POST /upload-media/init` (без изменений) →
  `POST /upload-media/{id}/part-urls` (`{upload_id, part_numbers:[...]}` → presigned PUT на
  каждую часть, клиент запрашивает URL всех недостающих частей одним запросом) → клиент
  грузит части **пулом по 6 одновременно** (`media_upload.dart`, `partConcurrency`, было 3
  до `1.0.0+37` — параллелизм ВНУТРИ одной загрузки, файловый воркер `PendingSendRetrier`
  по-прежнему один; части читаются ПОТОКОМ с диска, не целиком в память) напрямую в MinIO →
  `GET /upload-media/{id}/parts` + `POST /upload-media/{id}/complete`
  (без изменений — сервер собирает по `ListObjectParts`). Докачка/резюм — как раньше
  (истина у MinIO); упавшая часть перезапрашивает свой presigned-URL.
- Скачивание: `GET /media/{id}/url` → `{url, size_bytes}` (presigned GET, права проверяются
  как в `download_media.go` — только загрузчик/получатель). Клиент качает Range-докачкой по
  этому URL (`downloadEncryptedMediaResumable(directUrl: ...)`), presigned GET на 403
  (истёк, 2ч) → `_runOne` берёт свежий URL на следующей попытке.
- **Старые relay-эндпоинты (`POST /upload-media`, `PUT .../part/N`, `GET /media/{id}`)
  оставлены рабочими как fallback** — код клиента `uploadEncryptedMediaFileWithProgress` /
  `uploadChunkedPart` тоже пока не удалён. **Это не теоретический fallback** — см. ниже,
  реально отрабатывает у пользователей РФ без VPN на каждой части.

**MinIO-доступ сервера:** отдельный пользователь `oshino-server` (создан `mc admin user add`
на NAS) с политикой `oshino-media` — только бакет `e2ee-media`: на `e2ee-media/*` —
`s3:PutObject`/`GetObject`/`DeleteObject`/`AbortMultipartUpload`/`ListMultipartUploadParts`;
на `e2ee-media` — `GetBucketLocation`/`ListBucket`/`ListBucketMultipartUploads`. Не рут.
Тот же ключ используется и локальным клиентом (FRP), и presign-клиентом.

**Прочие ускорения на Москве (2026-09-03):** BBR + `fq` + расширенные TCP-буферы
(`/etc/sysctl.d/99-oshino-net.conf`: `tcp_congestion_control=bbr`, `default_qdisc=fq`,
`rmem_max`/`wmem_max` 8 МБ, `tcp_mtu_probing=1`, `tcp_fastopen=3`); в nginx server-блоке
`ee2e.oshino.space` — `proxy_request_buffering off`, `proxy_http_version 1.1`,
`proxy_read_timeout`/`send_timeout` 600s. (После presigned это в основном для WS/API —
байты файлов через Москву должны были перестать идти, но см. ниже: у части пользователей
РФ без VPN presigned-путь до Токио не работает вообще, и они грузят файлы через Москву
как раньше, той же дорогой, что и до этого решения.)

**Если проект вырастет:** написано ещё при Vultr Tokyo (упирался бы в 1 ТБ/мес трафика или
throttle, план побольше у Vultr) — после миграции 2026-09-05 на Sakura Osaka актуальный лимит
трафика/тарифный потолок именно у Sakura ещё не выяснялся, уточнить отдельно, если станет
актуально. Cloudflare Tunnel рассматривался и отклонён (Free-план не
даёт поддомен как зону; полная миграция `oshino.space` рискованна из-за почты/старого
сайта + автопродление TLS). Tailscale Funnel отклонён (недокументированный лимит
скорости, «funnel, не hose»).

## Ускорение передачи файлов — эксперименты и замеры (2026-09-04)

Живая, по фактам: что сделали, что реально измерили (с источником и условиями), что из
этого следует. Догадки помечены явно как догадки.

### Что сделали (код, в `1.0.0+37`)

1. **Аппаратный AES-256-GCM для файлов** вместо чистого Dart. `android/.../FileCipher.kt` —
   потоковый `javax.crypto` `AES/GCM/NoPadding` через MethodChannel `oshinobu/file_cipher`,
   формат блоков байт-в-байт как у `StreamingFileCipher.dart` (кросс-проверено тестом
   `test/streaming_file_cipher_interop_test.dart` — Dart↔Java в обе стороны, обрезанный файл,
   файл кратный размеру блока). `NativeFileCipher` + диспетчеризация в
   `StreamingFileCipher.encryptFileInIsolate`/`decryptFileInIsolate`: Android → нативно,
   иначе/при сбое → прежний чистый Dart в `compute`-изоляте. Только Android; на iOS нужен
   Swift-двойник (не сделан, см. roadmap).
2. **Части чанковой загрузки читаются потоком** с диска (`File.openRead(offset, end)`,
   новый поток на каждую попытку `_retryChunkedStep`), а не целиком в `Uint8List`.
3. **Параллельность частей 3 → 6** (`media_upload.dart`, `partConcurrency`).
4. **Транспорт для медиа-запросов → Cronet** (`native_dio_adapter` + `cronet_http`, только
   `ApiClient._mediaDioClient()`; auth/WS не тронуты). На Android — `cronet-embedded`
   (не `play-services-cronet`: у него конфликт namespace `org.chromium.net` с AGP 8, см.
   `android/app/build.gradle.kts`). HTTP/3 на relay-nginx включён (2026-09-05, изначально на
   Vultr Tokyo, после миграции 2026-09-05 — на Sakura Osaka, см. ниже) —
   Cronet сам решает, договориться ли с сервером на QUIC вместо HTTP/2, отдельного флага на
   клиенте для этого не нужно. Прогресс отправки теперь считается по ПОДТВЕРЖДЁННЫМ частям,
   а не «в полёте» — Cronet буферизует тело запроса целиком перед отправкой, из-за чего
   `onSendProgress` показывал бы ложные 100% заранее.

Замер #5 подтверждён логом (`debug_log.txt` того же прогона, см. ниже): **все ~29 частей
файла** упали на presigned-пути к `files.oshino.space` с `HandshakeException: Connection
terminated during handshake` и ушли на relay через `ee2e.oshino.space`. То есть 10 Мбит/с —
это скорость **московского relay**, а не токийского presigned-пути; про реальный потолок
presigned-пути с этого замера сказать ничего нельзя.

Замер #6 (Армения, `+37`, 66 Мбит/с) — это **единственный имеющийся чистый замер токийского
presigned-пути** после ускорений. Против замера #1 (тот же город, та же примерная схема, до
`+37`): шифрование 70 с → «почти мгновенно», загрузка 76 с → 35 с. **Итого по времени
файл-от-тапа-до-готово: 146 с → ~35 с, в 4 раза быстрее.** VPN в замере #6 пользователь не
уточнил — не путать с замером #1, где тоже не уточнялся.

### Что из этого следует (факт, не догадка)

- **Токийская инфраструктура (VPS + FRP-туннель + MinIO) способна отдавать ≥66 Мбит/с** —
  замер #6. Она не бутылочное горло для тех, кто до неё доходит.
- **У пользователя из Москвы (замер #5) без VPN presigned-путь к `files.oshino.space` НЕ
  РАБОТАЕТ** — TLS-рукопожатие обрывается на каждой попытке (`HandshakeException`), 100% частей
  падает в relay-fallback. Это видно из лога напрямую, не предположение.
- **У того же пользователя без VPN домен `ee2e.oshino.space` (Москва) периодически не
  резолвится DNS'ом** (`Failed host lookup ... errno=7`, повторялось десятки раз за 36 минут
  лога), WebSocket рвётся с кодами 1002/1006.
- **На узком аплинке (замер #2–4, ~6 Мбит/с) параллельность/Cronet не помогают и могут
  вредить** (замер #4) — канал и так насыщен, а буферизация Cronet добавляет CPU/RAM/нагрев без
  выигрыша.
- Спидтест «100 Мбит» из первого армянского упоминания — направление (входящая/исходящая) не
  уточнялось; более поздние спидтесты (замеры #2, #3, #5) показывают, что заявленная
  пользователем цифра часто относится к входящей скорости, а исходящая может быть кратно ниже
  (Япония: 97/6 и 60/6) или почти равна (Москва: 38/36).

### Проверка блокировки — только ICMP, не TLS/приложение

Два независимых `ping files.oshino.space` (202.182.112.9) от пользователей РФ без VPN:

| Город | Потери | RTT |
|---|---|---|
| Москва (тот же пользователь, что и замер #5) | 50% (2 из 4) | 273–289 мс |
| Казань | 0% | 278–387 мс (сильный джиттер) |

**Факт:** блокировка/деградация — не повсеместная по РФ, у разных провайдеров разное поведение.
**Не факт, а открытый вопрос:** `ping` — это ICMP, а не TLS; успешный пинг ничего не говорит о
том, проходит ли реальное HTTPS-соединение (DPI обычно блокирует именно TLS/SNI, ICMP часто не
трогает вообще). От Казани и других городов ещё не получен `curl`/браузерный тест на
`https://files.oshino.space/minio/health/live` — без него нельзя сказать, работает ли там
presigned-путь по-настоящему.

### Решение (2026-09-04)

- **Скоростные изменения `+37` (нативный AES, потоковые части, concurrency 6, Cronet) —
  оставляем**, откатывать не будем: замер #6 показал 4-кратное ускорение на чистом пути,
  а замер #4 (единственный, где стало хуже) — частный случай узкого аплинка, не целевой профиль.
- **Оба пути загрузки (presigned-Токио + relay-Москва) остаются** — это и так уже было
  устройство системы (fallback при ошибке presigned), просто теперь известно, что для части
  пользователей РФ relay — не запасной, а единственный путь.
- **Задача «сделать Токио достижимым из РФ без VPN» — отдельная, отложена до после релиза
  `1.0.0+38`.** Не решается тюнингом скорости (Cronet/QUIC/параллельность) — это доступность,
  не пропускная способность. **Решена (без изменения кода) 2026-09-05** — см. раздел
  «Расследование причины низкой скорости Москва↔MinIO» ниже: точечный личный VPN для узкого
  круга вместо системного решения для всех.

### Варианты для задачи доступности — обсуждались, ничего не реализовано

- **Разогнать существующий relay** (апгрейд московского VPS с 1 vCPU + туннель напрямую в
  MinIO, без Токио посередине). Отклонена промежуточная идея «Москва как обратный прокси на
  Токио» — если московский VPS всё равно терминирует TLS клиента, лишний хоп до Токио не
  ускоряет плечо до NAS сильнее, чем прямой апгрейженный туннель Москва→MinIO (международное
  плечо той же длины что там, что там). Диагностика (какое именно там горло — CPU VPS,
  туннель, NAS) начата (`top`, `mc cp` через туннель, `iperf3`) и приостановлена после замера
  #6 — токийская инфраструктура сама по себе не горло, вопрос сузился до доступности.
- **CDN (Cloudflare) перед доменами** — лимит тела запроса (100 МБ на Free/Pro) не пройдёт для
  файла целиком, но подходит для отдельных частей (≤8 МБ); presigned SigV4 через прокси
  Cloudflare рискует сломаться на переписывании заголовков — не проверено. RF периодически
  troттлит диапазоны Cloudflare.
- **Домен-фронтинг / ECH** — постоянная гонка с DPI, требует непрерывного обслуживания.
- **Хранилище ближе к РФ** (Япония — бэкап) — не начато, требует диска на VPS и логики
  репликации.
- **Второй дешёвый VPS у РОССИЙСКОГО хостера** (не тот же хостер/подсеть, что нынешний
  московский VPS — иначе от «запасного» IP пользы мало) как ещё один domestic-адрес про запас;
  предпочтительно тоже в Москве (лучший пиринг с остальной РФ через MSK-IX и подобные точки
  обмена). **Не апгрейд нынешнего VPS, а второй, независимый.**
  Идея пользователя «свой сервер дома + белый IP от провайдера» — рассмотрена и отклонена:
  домашний аплинк/надёжность/безопасность хуже дешёвого VPS при той же цели (внутрироссийский
  IP), плюс лишняя экспозиция домашней сети.
- Следующий диагностический шаг, если возвращаемся к этой задаче: TLS/HTTP-тест (не ping) с
  нескольких точек РФ, чтобы отличить «блокирует конкретный провайдер» от «блокирует
  повсеместно» — от этого зависит, чинить ли точечно или искать системное решение.

### Расследование причины низкой скорости Москва↔MinIO (2026-09-05) — и почему второй VPS не первый приоритет

Перед тем как поднимать второй VPS ради доступности, проверили — почему сама связка
Москва↔MinIO (через её собственный, локальный FRP-туннель до NAS, порт 7000, БЕЗ Токио
вообще) выдаёт всего ~18-19 Мбит/с, тогда как токийский путь показывал 66 Мбит/с
(замер #6). По шагам, с реальными замерами прямо на серверах:

1. **CPU/память московского VPS исключены полностью.** `mc cp` 100 МБ через
   `127.0.0.1:9000` (локальный конец FRP-туннеля) — 44.4с (~18.5 Мбит/с), при этом
   `user+sys` CPU-время за весь замер — 0.4с из 44.4с (`vmstat`: `id` 97-100% всё время),
   `swpd` не растёт. Сервер практически простаивает, пока идёт передача — 1 vCPU/1 ГБ
   ни при чём.
2. **Параллелизм НЕ помогает** — 4 одновременных `mc cp` по 100 МБ дали суммарно те же
   ~18-19 Мбит/с (не ×4, как было бы при упоре в BDP-лимит одного TCP-потока — та же
   логика, что чинили параллельностью частей для прямой заливки в Токио, здесь не
   сработала). Это исключает версию «упираемся в мультиплексирование одного FRP-потока».
3. **Явного лимита в конфиге FRP нет** — ни `bandwidthLimit` в `frpc.toml` на NAS
   (`/mnt/tank/e2ee/scripts/frpc/frpc_e2ee.sh`), ни в `frps.toml` на Москве.
4. **Неожиданный факт, разворачивающий диагноз:** тот же самый NAS через ДРУГОЙ туннель
   (`frpc-e2ee-tokyo`) от токийского VPS принимает 66 Мбит/с без проблем (замер #6 —
   тот же физический аплинк NAS). Значит, дело НЕ в физическом потолке домашнего
   интернета NAS (та версия отпадает) — узкое место специфично именно для пути
   Москва↔конкретно-этот-NAS или, как выяснилось дальше, вообще для пути
   Москва↔конкретно-Vultr-Токио.
5. **Прямой тест Москва↔Токио (`nc`, минуя FRP/MinIO/NAS вообще) — тоже сломан**, но
   иначе: голый TCP на нестандартный порт зависал НАСМЕРТЬ (5+ минут, 0 прогресса,
   `Connection refused` сразу после — то есть соединение до этого реально
   устанавливалось и тут же замирало). `mc cp` через настоящий продакшн-путь
   (HTTPS/443 на `files.oshino.space`, реальный домен/эндпоинт) — не зависает, но ползёт
   и УГАСАЕТ (160 КиБ/с → 20 КиБ/с), классическая картина троттлинга, а не жёсткого
   лимита.
6. **Тест с WireGuard-туннелем Москва↔Токио (SNI-гипотеза) — не помог.** Подняли голый
   WireGuard (не для продакшна — только проверить гипотезу), внутри погнали тот же файл
   на приватный IP туннеля: получили ТОЧНО ТАКУЮ ЖЕ картину, что и голый TCP без VPN —
   несколько КБ и полная тишина (`wg show`: `received` не растёт, только keepalive).
   Раз даже полностью зашифрованный, не показывающий никакого SNI/домена трафик до ТОГО
   ЖЕ IP тоже умирает — **дело не в TLS-SNI-инспекции конкретно `files.oshino.space`**,
   а вероятнее всего в блокировке/троттлинге по IP-диапазону/ASN самого Vultr (известная
   практика части провайдеров РФ — резать известные VPS/хостинг-диапазоны целиком,
   независимо от протокола и содержимого, потому что через них массово идут VPN/обход
   блокировок). Домашний IP NAS в Японии (не «подозрительный» хостинг-ASN) при этом
   спокойно работает.
7. **Тестовая инфраструктура убрана** — WireGuard, тестовые файлы, временные правила
   `ufw` (5002/tcp, 5003/tcp, 51820/udp) на обеих машинах снесены после теста.

**Решение, принятое в моменте (2026-09-05, позже пересмотрено ниже же в тот день):** не
чинить это со стороны сервера/протокола — ни второй VPS (унаследует ту же ASN-проблему,
если у похожего хостера), ни VPN/обфускация между серверами (гипотеза проверена и не
подтвердилась на Vultr) не дают предсказуемого выигрыша. Вместо этого — точечный личный
VPN для узкого круга (AmneziaVPN/WireGuard в Германии), обычные пользователи остаются на
fallback через Москву, код не менять.

**Что изменилось в тот же день:** пока разбирались, почему relay Москва↔MinIO медленный
(см. предыдущий раздел), заодно замерили Sakura Osaka↔NAS — оказалось быстро (~90-100
Мбит/с, см. ниже). А отдельно проверили саму идею личного VPN для узкого круга — и
внезапно выяснилось, что **сам Vultr Tokyo не принимает VPN-трафик из РФ** (та же
ASN-блокировка, что и обычный HTTPS — см. «Миграция» ниже). Раз всё равно нужен был
другой сервер под VPN, а Sakura Osaka под него уже поднялась и показала хорошую скорость
до NAS — решили не размениваться на два отдельных исправления, а **заменить Vultr Tokyo
на Sakura Osaka целиком**, отдав ей и роль relay, и роль VPN-сервера для личного круга.
Подробности — сразу следующий раздел. Задача «доступность Токио [Vultr] из РФ без VPN»
в исходной форме закрыта тем, что Vultr Tokyo для файлового relay больше не используется
вообще.

## Миграция relay-VPS с Vultr/Tokyo на Sakura/Osaka (2026-09-05)

**Итог:** `files.oshino.space` теперь обслуживается **Sakura Osaka** (`49.212.216.161`)
вместо Vultr Tokyo (`202.182.112.9`). На той же машине также поднят AmneziaWG-сервер для
личных VPN-подключений узкого круга людей (см. предыдущий раздел) — то есть один VPS
теперь совмещает обе роли: relay для файлов ВСЕХ пользователей + VPN-выход для нескольких
доверенных людей. Vultr Tokyo решено пока не удалять сразу — подождать несколько дней
стабильной работы Sakura, прежде чем отменять подписку.

**Почему не Vultr:** уже было известно (см. предыдущий раздел), что Vultr Tokyo,
предположительно, в чёрных списках у части сетевой инфраструктуры РФ на уровне
IP/ASN — режется не только обычный HTTPS-трафик к `files.oshino.space`, но и голый TCP,
и даже WireGuard-туннель до того же IP (тест был датацентр↔датацентр, Москва↔Vultr).
Решающая проверка в тот же день: пользователь поставил AmneziaVPN-совместимое приложение
("DefaultVPN" — официальная альтернатива Amnezia на случай, если их приложение недоступно
в App Store конкретной страны) на РЕАЛЬНЫЙ телефон в РФ и подключился к свежесозданному
AmneziaWG-серверу на Vultr Tokyo — **не заработало** (сайты не открывались). Тот же
телефон, то же приложение, конфиг друга на VPS в Германии — заработало сразу. Это и есть
прямое, а не косвенное подтверждение: дело не в конкретном хостере "этой" московской VPS
(единственная альтернативная версия, которая оставалась после датацентрового теста), а в
самом Vultr/Tokyo.

**Почему Sakura:** локальный японский хостер (さくらのVPS, один из старейших в Японии,
не позиционируется международно как "VPN-friendly" хостинг, в отличие от Vultr/
DigitalOcean/Linode) — гипотеза, что такие провайдеры реже попадают в подобные
блок-листы именно потому, что ими не пользуются международные VPN-сервисы массово.
Гипотеза подтвердилась и для VPN (реальный телефон из РФ), и для обычного relay-трафика
(см. замеры ниже) — обе проверки прошли чисто.

**Замер скорости Sakura↔NAS (до начала миграции, гейт перед решением мигрировать)**:
сырой `nc`-тест 100 МБ, направление совпадает с продакшн-потоком (Sakura отправляет,
NAS принимает — тот, кто инициирует TCP-соединение, из-за NAT NAS всегда сам, но кто
реально шлёт байты — не связано с тем, кто дозвонился). Результат: **RTT ~40 мс**
(на порядок лучше любого международного пути, что мерили раньше), `bytes_sent =
bytes_acked` (полная доставка, 0 потерь), BBR оценивает канал в **~90-100 Мбит/с**
(`delivery_rate 88.5Mbps` по `ss -ti`). Для сравнения: Москва↔NAS через свой FRP-туннель
— ~18-19 Мбит/с; лучший замер Vultr Tokyo (Армения→Tokyo) — 66 Мбит/с. Sakura Osaka
оказалась и надёжнее (не заблокирована из РФ), и быстрее по факту замера.

**Ход миграции (последовательность, которая сработала):**
1. NAS: скрипт `frpc-tokyo` (`/mnt/tank/e2ee/scripts/frpc-tokyo/frpc_tokyo.sh`)
   переименован в `frpc-osaka/frpc_osaka.sh` (`sed 's/tokyo/osaka/g'` — все вхождения
   слова были ровно там, где нужно: имя контейнера, `CONFIG_DIR`, имя прокси).
   `.env` обновлён: новый `FRP_TOKEN` (сгенерирован заново, не унаследован от Vultr),
   `FRPS_ADDR` → IP Sakura. Контейнер `frpc-e2ee-tokyo` при запуске скрипта заменился на
   `frpc-e2ee-osaka` (тот же docker-механизм `docker rm -f` + `docker run --name`, просто
   под новым именем) — то есть отдельный "новый" контейнер НЕ заводили, переиспользовали
   существующий слот.
2. Sakura: `frps` v0.70.0 (та же версия, что везде) — бинарь с GitHub releases (не из
   apt), `/e2ee/frps/frps` + `frps.toml` (bindPort 7000, тот же формат, что на Vultr) +
   systemd-юнит `e2ee-frps.service` (скопирован с Vultr текстуально, только "Tokyo"→
   "Osaka" в Description).
3. Проверка туннеля ДО домена/сертификата: `curl http://127.0.0.1:9000/minio/health/live`
   на Sakura — 200 OK, туннель подтверждён рабочим независимо от DNS/nginx.
4. nginx на Sakura: сначала голый HTTP (порт 80, тот же `location /` блок, что на Vultr,
   с критичными для SigV4 `proxy_request_buffering off`/`proxy_buffering off`/
   `client_max_body_size 0`/`proxy_set_header Host $host`), проверено через
   `curl -H "Host: files.oshino.space" http://127.0.0.1/...` — ДО переключения DNS,
   чтобы не городить домен на непроверенный конфиг.
5. DNS (Route53) переключён на Sakura ТОЛЬКО после проверки шага 4 — по порядку это
   предпоследний шаг, не первый (важно: Let's Encrypt не выпустит сертификат, пока DNS не
   указывает на сервер, значит HTTPS физически нельзя настроить раньше DNS — но и DNS
   раньше рабочего nginx переключать незачем, отсюда такой порядок).
6. `certbot --nginx -d files.oshino.space` — сработал с первого раза, сертификат выпущен
   и автоматически развёрнут.
7. HTTP/3 — см. отдельно ниже, потребовалась замена самого пакета nginx.

**Три конкретные ошибки, которые реально были допущены при миграции (для будущего, если
будете повторять на другом хостере):**
- **У Sakura ДВА независимых firewall** — `ufw` внутри сервера И "パケットフィルター"
  в панели управления (облачный, отдельно от ОС). Порт нужно открывать в ОБОИХ местах.
  Реальный кейс: 443/tcp добавили в панель, но забыли `sudo ufw allow 443/tcp` — снаружи
  (с Москвы) соединение тихо висело (`context deadline exceeded`), хотя с самой Sakura
  всё работало (трафик к собственному публичному IP обычно заворачивается через
  loopback, `ufw`-правила для внешнего интерфейса на него не действуют — отсюда и ложное
  "с сервера же работает").
- **Пакет nginx.org переписывает `/etc/nginx/nginx.conf`** на свой дефолтный at установке
  — тот инклюдит только `/etc/nginx/conf.d/*.conf`, БЕЗ `sites-enabled`. Конфиг сайта
  (лежащий в `sites-enabled`, как на Debian/Ubuntu-native nginx) молча переставал
  подключаться. Починено добавлением `include /etc/nginx/sites-enabled/*;` обратно в
  `http {}` блок вручную.
- **Один и тот же AmneziaWG `.conf`-файл нельзя ставить на два устройства** — сервер
  видит один и тот же криптографический ключ пира с разных адресов как "пир переехал",
  и молча отключает предыдущее устройство. На каждое физическое устройство — свой
  клиент (`manage_amneziawg.sh add <имя>`).

**HTTP/3 на Sakura — понадобился отдельный источник пакета.** Штатный nginx 1.24.0 из
репозитория Ubuntu 24.04 собран БЕЗ `--with-http_v3_module` (в отличие от Vultr, где
Ubuntu 26.04 уже шла с QUIC "из коробки"). Поставили из официального репозитория
nginx.org (mainline-ветка, apt-pinning priority 900) — версия 1.31.5, с QUIC. Именно
это обновление и снесло `sites-enabled` из `nginx.conf` (см. выше). После починки —
те же директивы, что и на Vultr (`listen 443 quic reuseport`, `http3 on`, `quic_retry
on`, `Alt-Svc`), подтверждено `curl`-ом.

**Побочный эффект:** заодно поднят AmneziaWG-сервер на этой же Sakura VPS — сначала
временно для эксперимента с VPN-гипотезой, потом решили не сносить и оставить как

других сервисов там ещё не было, ломать было нечего.

**Код:** `checkTokyoRelay` в `server/cmd/admin/check_project_services.go` переименован в
`checkFileRelay` (сообщения в консоли — нейтральные, без привязки к конкретному городу,
